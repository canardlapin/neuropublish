# Neuropublish publication protocol — core 0.1

This directory is the normative protocol (ADR 0001, architecture "Protocol as
the product boundary"). It is language-neutral: a producer needs a file, a JSON
writer, and SHA-256.

| Artifact | Path |
| --- | --- |
| Manifest structure | `schemas/manifest.schema.json` (`https://neuropublish.org/schema/0.1/manifest.schema.json`) |
| Saved view record | `schemas/workspace-state.schema.json` (`org.neuropublish.view/workspace-state@1`) |
| Rendition headers | `schemas/rendition-header.schema.json` (`org.neuropublish.rendition/volume-f32@0`, `surface-mesh@0`, `vertex-field-f32@0`; §5 "Renditions") |
| Trusted record schemas | `schemas/records/volume-grid-v1.schema.json` (`org.neuropublish.domain/volume-grid@1.0`; `$id` `https://neuropublish.org/schema/0.1/records/volume-grid-v1.schema.json`, changed from the earlier `urn:neuropublish:…` form so every schema id lives under one base); `schemas/records/surface-vertices-v1.schema.json` (`org.neuropublish.domain/surface-vertices@1.0`) |
| Invariants the schemas cannot state | this file |
| Golden fixtures | `modules/conformance/fixtures/{reference,valid,invalid,old-version,new-extension,schema-digest-mismatch,julia}`; each `invalid/*.json` has a `.expect` listing the exact problems admission must report, one per line, in order, each a prefix of the rendered `<pointer>: <message>` (a whole-document problem has no pointer prefix) |
| HTTP control plane | `modules/api-contract` (Tapir; OpenAPI generated by the backend) |

The Scala modules implement this document; they do not define it. The JVM
implementation (`protocol-json`, server, `npub`) runs every stage below. The
Scala.js build runs everything except JSON Schema validation (decoder, closure,
and semantic checks only); it is a consumer, not an admission authority.

## 1. Bundle

```text
<name>.npub/
├── manifest.json
└── assets/sha256/<xx>/<hex>      # one file per canonical asset, named by digest
```

A *staging* bundle may instead carry `assets[].path` (a file relative to the
staging directory), or a `digest` whose bytes already sit at
`assets/sha256/<xx>/<hex>` under the staging directory. `npub pack` hashes
each file (streamed), writes the normalized layout, fills `digest` and `size`,
removes `path`, and refuses — before writing anything — a path that escapes the
staging directory or is not a regular file, an asset with neither `path` nor
`digest`, a digest-only asset whose bytes are not staged, a declared `digest`
or `size` that disagrees with the file (declarations are never overwritten), a
non-array `assets`, and an existing output bundle unless `--force` is given. A
committed manifest never carries `path` (`invalid/local-path`).

## 2. Byte profile and identity

The manifest digest is SHA-256 over the exact bytes of `manifest.json` as the
producer wrote them; there is no canonicalization, and the digest travels in
upload-session metadata, never inside the file. The bytes are admitted only if:

- UTF-8 without a byte order mark, with no invalid or overlong sequences;
- exactly one root object and no trailing content;
- no duplicate keys in any object (reported at the pointer of that object);
- only Unicode scalar values (no lone surrogate escapes);
- only finite numbers, written per RFC 8259 (no leading zeros, no NaN/Infinity).
  "Finite" is a property of the text: any decimal the grammar admits is
  accepted, however large its exponent. Readers bind numbers to the widest
  type they have (IEEE-754 double for the reference implementation), so a
  magnitude beyond that range reads as infinity and a precision beyond it is
  rounded; a producer that needs exactness beyond a double writes a string;
- nesting no deeper than 512 levels (`ByteProfile.Scanner.MaxDepth`), so a
  reader never risks a stack overflow on hostile input.

Size: an upload session declares `manifestSize`; the server refuses a manifest
whose byte count differs from the declaration, and the session limits the API
declares (`Limits`: object size, object count, session size) bound what a
session may carry. There is no separate manifest byte cap beyond those today.

Whitespace and key order change the digest but not the parsed form; semantic
comparison is a parsed-form operation and never an identity claim. The server
stores the admitted bytes immutably and returns them unchanged.

Asset identity is `sha256:<64 lowercase hex>` over the asset bytes. The
manifest commits transitively to every asset through those digests.

## 3. Admission pipeline

Admission runs every stage it can and reports the union of problems; it never
stops at the first one. Every problem is `(pointer, message)` with an RFC 6901
JSON Pointer into the manifest (`""` is the whole document; a missing required
member is reported at the member's pointer, e.g. `/assets/1/digest`). The CLI
prints `error  <pointer>: <message>` per problem; the API returns them in
`ApiError.problems`.

1. byte profile (§2);
2. JSON parse;
3. core version and migration (§8);
4. JSON Schema 2020-12 validation against `manifest.schema.json`;
5. structural decode into the reference projection;
6. reference closure (§4);
7. semantic checks (§5), including recomputation of every trusted domain key
   that the manifest alone determines (§6) and validation of every trusted
   record payload against its records schema.

A key that depends on asset bytes (`surface-vertices/v1`, §6) is verified at
ingestion, after the assets are stored: admission proves what the manifest can
prove, and the revision's ingestion fails — never silently succeeds — when the
bytes disagree.

A pointer is reported once: where the schema and a semantic check speak to the
same member, the schema's finding stands (except that the raw-JSON checks for
`catalog`/`path`, which name the remedy, take precedence).

**JS-lenient subset.** The Scala.js build has no JSON Schema validator, so
stage 4 is empty there. Its structural decoder (stage 5) still enforces the
schema rules the projection depends on — required members (including
`resultFields[].selection`), the `sha256:` digest grammar, the schema-reference
`version` grammar, non-negative `size`/`sampleSize`, trusted-record payload
structure — and all of stages 6–7. What only the JVM rejects: enum and pattern
violations on members the projection does not act on (`localId`, `semanticId`
outside `measure`, `mediaType`, `colormap`, `threshold.mode`), closed-structure
extras (`additionalProperties: false`), `minItems`/`minLength`/`uniqueItems`,
and records-schema constraints beyond the fingerprint fields. A browser that
admits a manifest has therefore not admitted it; the server has.

## 4. Reference closure

- every `resultFields[].representations[].asset`, `underlays[].asset`, and
  `surfaces[].asset` names a declared `assets[].id`;
- every `resultFields[].domain`, `underlays[].domain`, and `surfaces[].domain`
  names a declared `domains[].id`;
- every `resultFields[].representations[].surface` names a declared
  `surfaces[].id`, and `…representations[].derivation`, when present, a
  provenance activity;
- every `resultFields[].estimand` names an estimand declared by some analysis;
- every `warnings[].concerns.{analysis,field,provenance}` names an analysis,
  result field, or provenance entity/activity respectively;
- every `provenance.edges[].{from,to}` names a provenance entity, activity,
  asset, or result field.

## 5. Semantic invariants

- Ids are unique within their list: assets, domains, surfaces, analyses,
  result fields, warnings, provenance entities, provenance activities;
  estimand ids are unique within their analysis.
- `sensitivity` is required: `group-level` or `subject-level`. Only
  `group-level` snapshots may be link-shared; the policy is enforced at commit
  and at share creation.
- `measure` is a semantic id (§7). The built-in trusted measures are
  `org.neuropublish.measure/{effect,standard-error,t-statistic,z-statistic,p-value,accuracy,correlation}`;
  an unknown measure is shown by its id and grants no inferential behavior.
- `catalog` on an asset is informational once `digest` is present; an asset
  with a catalog reference and no digest was never resolved and is rejected
  (`invalid/catalog-unresolved`).
- `publishedDisplay` is a recommendation: `threshold.mode` is one of
  `two-sided | positive | negative | off`, `threshold.min >= 0`,
  `window.min < window.max` is expected by viewers, `colormap` is a closed
  URL-safe grammar, and `opacity`, when present, is in `[0, 1]`. None of it is
  an inferential rule. A viewer applies every member it accepts: a value read
  from the manifest and then replaced by the viewer's own default would show
  the producer a recommendation they never made, which is the failure a closed
  structure exists to prevent.
- `publishedDisplay.window.centre` names the value the colour scale is centred
  on. In core 0.1 it must be the window midpoint `(min + max) / 2`, compared to
  within `1e-9 * max(1, |min|, |max|)` so a centre written to the precision a
  producer can emit still counts; a centre anywhere else is rejected
  (`invalid/window-centre-offset`) rather than accepted and ignored, because
  this version renders one linear ramp across `[min, max]`. A later core
  version lifts the restriction when the upstream diverging-palette work lands
  (`docs/architecture.md`, "Viewer integration and upstream gaps"); until then
  the field is legal, checked, and never misleading.

### Ordering

Estimands within an analysis and result fields (measures) within an estimand
are ordered by their explicit integer `order`; entries without `order` follow
all ordered ones; ties (including the absence of `order`) are broken by array
position. `order` values must be unique among an analysis's estimands and among
the fields of one estimand. Readers must not reorder by label, id, or measure.

### Warning scope

A warning may carry `concerns`, a pointer to what it is about: `analysis`,
`field`, or `provenance` (a manifest-local id). A warning without `concerns`
applies to the snapshot as a whole. Interfaces surface a warning wherever its
scope is shown (overview, result tree, provenance).

### Surfaces

`surfaces[]` declares the geometries surface representations are shown on:
`{id, asset, domain, hemisphere, kind, label}` — a GIFTI asset (POINTSET
float32 + TRIANGLE int32, ASCII or Base64 encoded) on a trusted
`surface-vertices` domain (§6) whose `hemisphere` it must match (`left` |
`right`; `invalid/surface-hemisphere-mismatch`,
`invalid/surface-domain-not-surface`); `kind` is `pial | white | midthickness
| inflated`. Several surfaces (white, pial, inflated) may realize one domain;
each must carry the domain's triangles exactly, which is proven at ingestion.
An `id` is not an `asset`: the reference bundle's `lh-pial-surface` sits on
asset `lh-pial`, and what a member names — an entry or an asset — is stated
wherever the two could be confused.

One asset is one thing. An asset backs at most one `surfaces[]` entry
(`invalid/surface-asset-shared`: two entries would derive one geometry
rendition and quietly take one of their hemispheres for it), and an asset that
is a surface geometry is not also an underlay, a volume representation, or a
vertex field (`invalid/surface-asset-two-roles`): the server derives one
rendition per asset, so a second role would be dropped without a word.

A representation of `kind: "surface"` carries `surface` (a `surfaces[].id`)
and `hemisphere`, which must equal the surface's
(`invalid/representation-surface-undeclared`,
`invalid/representation-surface-hemisphere`); its asset is a GIFTI with one
scalar per vertex of that surface (`NIFTI_INTENT_NONE` or any non-geometry
data array; the vertex count is checked at ingestion). Left and right fields
are two representations of the same result field, one per hemisphere; a field
with no surface representation has no surface display — readers show an
honest empty state, they do not project. The representation's support is its
surface's domain, not the field's `domain`. `derivation` is optional and names
the provenance activity that produced the values
(`invalid/representation-derivation-unknown`); its absence declares a native
surface measurement, not a missing receipt — admission cannot tell a measured
field from a projected one, so requiring the member would only move the claim
one field over. `surface` and `hemisphere` are refused on any other
representation kind.

**What ingestion requires of the bytes.** A surface geometry and a vertex
field are read on the JVM, and what the manifest cannot prove is proven there
(§6, "admission split"), each failure naming the asset and refusing the
revision:

- *float32 sources only in this revision.* A `NIFTI_TYPE_FLOAT64` POINTSET or
  vertex-field array is refused ("this revision reads float32 GIFTI sources
  only (write NIFTI_TYPE_FLOAT32)"); the reference GIFTI reader decodes
  `NIFTI_TYPE_FLOAT32`, `NIFTI_TYPE_INT32`, and `NIFTI_TYPE_UINT8`. NIfTI
  volumes are unaffected: a float64 volume is read and narrowed to float32 in
  its rendition, and the canonical asset remains the record.
- *dense fields only.* A `.func.gii` carrying a `NIFTI_INTENT_NODE_INDEX`
  array is a sparse field — the layout Workbench and nibabel write for values
  on part of a surface — and is refused by name rather than having its vertex
  indices stored as values. The field array (the first that is neither
  POINTSET nor TRIANGLE) must be rank 1, or rank 2 with `Dim1 = 1`: a V×T
  `NIFTI_INTENT_TIME_SERIES` is refused for what it is, never through a
  vertex-count message.
- *the hemisphere must survive the bytes.* Where the GIFTI states
  `AnatomicalStructurePrimary` (on the POINTSET array or the document), it must
  agree with the declared hemisphere: `CortexLeft` with `left`, `CortexRight`
  with `right`, anything else (`CortexLeftAndRight`, a cerebellar structure)
  refused. Left and right meshes of one template share a vertex count and a
  topology, so a swapped hemisphere is otherwise undetectable. A GIFTI that
  says nothing is taken at the manifest's word.
- *world coordinates are computed, not assumed.* The GIFTI's
  `CoordinateSystemTransformMatrix` is applied to the positions at
  ingestion — the one place it is applied — when its `TransformedSpace` is one
  this build can place in RAS+ millimetres (`NIFTI_XFORM_SCANNER_ANAT`,
  `NIFTI_XFORM_ALIGNED_ANAT`, `NIFTI_XFORM_TALAIRACH`, `NIFTI_XFORM_MNI_152`).
  The rendition payload is therefore world positions, its `surfaceToWorld` is
  the identity, and the matrix with both space names is kept as
  `sourceTransform` for provenance — a reader that composes through
  `surfaceToWorld` (picking, linking) cannot apply the transform twice. A
  transform into any other space (`NIFTI_XFORM_UNKNOWN` above all) is refused
  unless it is the identity and so says nothing; the label `RAS+` is a
  statement about the payload, and nothing writes it over a guess.

### Canonical versus derived representations

`assets` are canonical: they are in the digest and they are the scientific
record. A representation's `kind` (`volume | surface | table | preview`) says
how an asset presents a field on its `domain`. Anything the server derives
(browser renditions, previews, scalar summaries) is recorded on the revision
with source digests, converter version, and parameters, and is outside the
snapshot digest. A producer may ship precomputed derivatives; the server treats
them as untrusted and recomputes or verifies them. A representation on a
support other than the field's domain must reference an explicit mapping or
derivation (ADR 0005 §3); in core 0.1 a volume representation is on the
field's own domain and a surface representation is on its surface's domain
with the producer's `derivation` as the receipt ("Surfaces" above).

### Renditions

The server derives one browser-ready rendition per asset it can read, named
by the asset id (`/api/v1/revisions/{rev}/renditions/{asset}/{header,payload}`)
and listed on the revision with `kind` and, for vertex fields, `surface`:

| `kind` | Source | Profile (header JSON) | Payload (little-endian) |
| --- | --- | --- | --- |
| `volume` | `underlays[]` and volume representations (NIfTI) | `org.neuropublish.rendition/volume-f32@0`: `shape`, `affine`, `dtype`, `byteOrder`, `order`, `missing`, `source`, `summary` | float32 × shape product, x-fastest, NaN missing |
| `surface-mesh` | `surfaces[]` (GIFTI geometry) | `org.neuropublish.rendition/surface-mesh@0`: `hemisphere`, `kind`, `space`, `vertexCount`, `faceCount`, `surfaceToWorld` (4×4 row-major, the identity), `coordinateSystem: "RAS+"`, `topologyIdentity`, `faceDigest`, `sourceTransform`, `anatomicalStructurePrimary`, `source` | float32 × 3·V world positions (vertex order), then int32 × 3·F vertex ordinals (face order) |
| `vertex-field` | surface representations (GIFTI scalars) | `org.neuropublish.rendition/vertex-field-f32@0`: `surface` (the `surfaces[].id`), `vertexCount`, `summary`, `source` | float32 × V, vertex order, NaN missing |

A `surface-mesh` payload is world positions: `surfaceToWorld` is the identity
and `sourceTransform` records the GIFTI transform ingestion applied
("Surfaces" above), so composing a pick through `surfaceToWorld` stays correct
and applies nothing twice. `space` is the surface's domain `space`; a reader
compares it with a volume's before it links the two by world millimetres.
`anatomicalStructurePrimary` is what the GIFTI said, verified against the
declared hemisphere at ingestion.

Two topology keys are carried, and they are not interchangeable.
`faceDigest` is the SHA-256 of the payload's face bytes (little-endian int32
ordinals in face order): a cryptographic identity that does not depend on any
implementation's hash seeds, and the one a decoder must verify when it is
present. `topologyIdentity` is the reference implementation's key of the
ordered faces (ScalaFIM `MeshTopologyIdentity.stableKey`, a 64-bit
non-cryptographic hash); a decoder rebuilds the mesh and must arrive at the
same key, and a ScalaFIM change that moved it would be a rendition-profile
change, not a silent one. `summary` is the server-derived `ScalarSummary`
(min, max, quantiles, histogram, counts). All three headers validate against
`schemas/rendition-header.schema.json`. A float64 NIfTI volume loses precision
in its rendition and the canonical asset remains the record; a float64 GIFTI
source is refused outright in this revision ("Surfaces" above).

`space` is required on a `surface-mesh@0` header and the decoder refuses one
without it. Renditions written before `space` existed therefore no longer
decode and must be re-derived from their canonical assets — a rendition is
server-derived, outside the snapshot digest, and always reproducible, while an
unlabelled space is the dishonesty this member exists to remove: a reader that
defaulted it to "compatible" would link a surface to a volume of another space
exactly as before. The profile stays at `@0`, the band in which a header may
gain required members and stored renditions are re-derived rather than
migrated.

## 6. Domains (ADR 0005 §1)

Every `domains[]` entry has a manifest-local `id`, an open `descriptor`
record, and (when the descriptor is trusted) an exact `key`:

```json
"key": {"descriptor": {same schema ref as descriptor.schema},
        "size": <element count>,
        "structuralFingerprint": "sha256:…"}
```

For a trusted descriptor the key is required: `key.descriptor` must equal
`descriptor.schema` (id, version, digest), `key.size` must equal the element
count (for `volume-grid/v1`, the product of `shape`; for `surface-vertices/v1`,
`vertexCount`), and `key.structuralFingerprint` must equal the fingerprint
recomputed from the descriptor. A disagreement is a problem at
`/domains/i/key/descriptor`, `/domains/i/key/size`, or
`/domains/i/key/structuralFingerprint`; a missing key at `/domains/i/key`; a
payload the records schema rejects at the offending member under
`/domains/i/descriptor/payload` (`invalid/domain-key-*`,
`invalid/domain-payload-shape`, `invalid/surface-key-size`). A domain whose
descriptor is unsupported carries whatever key it likes; nothing is recomputed.

The fingerprint is SHA-256 over a descriptor-specific binary preimage, never
over JSON. Version-1 preimages begin with the eight bytes `NPUDOM1\0`, use
little-endian integers and IEEE-754 doubles, encode each string as a uint32 byte
length followed by UTF-8, and append the descriptor id and version before the
descriptor's own values. For `volume-grid/v1`: space id, coordinate convention,
spatial unit, ordinal layout, three int32 shape values, sixteen row-major
float64 affine values (non-finite values invalid, negative zero written as
positive zero). For `surface-vertices/v1` (payload `{space, hemisphere,
vertexCount, faceCount, topology}`, `topology` the `asset` of a `surfaces[]`
entry on this domain carrying the payload's hemisphere — an `assets[].id`,
never a `surfaces[].id`, because the fingerprint is a function of that asset's
bytes; `invalid/surface-topology-surface-id`): space id, hemisphere, uint64
vertex count, uint64 face count, then every triangle of the `topology` asset
as three uint32 vertex ordinals in face-array order — and nothing of the
coordinates, so white, pial, and inflated geometries of one hemisphere share
a domain. The
server recomputes the fingerprint; a producer-supplied fingerprint with no
verifiable source is insufficient. An unknown descriptor is retained and
inspectable but gains no rendering or alignment behavior.

**Spaces.** A surface and a volume in one revision are linked by world
millimetres — a surface pick moves the volume cursor, and back — which
means something only when both are in the same space. Every `surface-vertices`
domain's `space` must therefore equal every `volume-grid` domain's `space` in
the same manifest, refused at `/domains/i/descriptor/payload/space`
(`invalid/surface-space-mismatch`). A manifest with no volume domain has
nothing to disagree with. The rendition header carries the space onward so a
reader can refuse the link defensively.

**Admission split.** The `volume-grid/v1` fingerprint is a function of the
descriptor, so admission recomputes it. The `surface-vertices/v1` fingerprint
is a function of the topology asset's bytes, which admission does not open (the
manifest is admitted before its assets are stored; GIFTI is decoded on the
JVM). Admission therefore checks the payload against its records schema, that
`key.descriptor` agrees, that `key.size` equals `vertexCount`, that
`structuralFingerprint` is a well-formed `sha256:` identity, and that
`topology` is the asset of a declared surface on this domain with the same
hemisphere (`invalid/surface-topology-undeclared`). Ingestion then reads
every surface's GIFTI, checks its vertex and face counts against its domain,
recomputes the fingerprint from its triangles, and refuses the revision
(ingestion status `failed`, the message naming the surface and both
fingerprints) when it
disagrees; it likewise refuses a vertex-field asset whose value count is not
its surface's vertex count. In worker mode the commit has already moved the
head, so the revision is visible with a failed ingestion and no renditions; in
inline mode the push itself fails. A browser that has admitted a manifest has
therefore not verified its surface domains; the server's ingestion has.

## 7. Open semantic records and trust

A semantic id is `namespace.segments/path-segments`:
`^[a-z][a-z0-9]*(\.[a-z][a-z0-9-]*)+(/[a-z0-9][a-z0-9-]*)+$`. An open record is
`{"schema": {"id", "version", "digest"?}, "payload": {…}}`; payload contents are
never constrained by the core schema (`unevaluatedProperties: true`).

Interpretation is explicit and closed over three states:

- **understood** — `schema.id` and `version` are in the implementation's
  trusted list and `schema.digest` equals the trusted schema document's
  SHA-256; typed interpretation is enabled;
- **unsupported** — the id is outside the `org.neuropublish.*` namespace
  (exact segment match: `org.neuropublish` or `org.neuropublish.<sub>`); the
  record is retained byte-for-byte, shown generically, and enables no
  scientific operation, whether or not it carries a digest;
- **invalid** — the id is in the trusted namespace but the id is unknown, the
  version is unknown, or the digest is absent or differs
  (`schema-digest-mismatch/trusted-volume-grid`); admission fails. An absent
  digest on a trusted-namespace record is a mismatch, not an opt-out: a record
  cannot grant itself trust by naming a trusted id, and it cannot dodge the
  check by omitting the digest.

The trusted digest is the SHA-256 of the records schema file exactly as
committed under `protocol/schemas/records/` (for `volume-grid@1.0`,
`records/volume-grid-v1.schema.json`; for `surface-vertices@1.0`,
`records/surface-vertices-v1.schema.json`; `FixtureSuite` pins
`TrustedSchemas` to the files' bytes). Editing a trusted schema therefore changes its digest and
every manifest that names it.

## 8. Compatibility and migrations

`core` is `major.minor`. An implementation at `0.n`:

- reads `0.m` for `m >= n` as is: a newer minor may only add members, which
  the reader preserves as unknown fields (`new-extension/`);
- brings `0.m` for `m < n` forward through migrations, one minor at a time;
  each migration is a pure JSON-to-JSON step that renames or restructures,
  never drops, members, and the result carries `migratedFrom: "<original
  core>"`. The stored snapshot and its digest are the original bytes; a
  migration changes only the parsed form a reader acts on. An older minor with
  no migration is rejected at `/core` with a clear message. Problems found
  after a migration address the migrated form (the pointers of the renamed
  members, not the original spelling);
- rejects any other major at `/core`, naming the major it cannot read, before
  any migration is attempted;
- rejects a document that already carries `migratedFrom` at `/migratedFrom`
  (`invalid/migrated-from-claimed`): the member is stamped by a reader, never
  written by a producer, so a migrated parsed form can never be re-stored as
  if it were the producer's bytes.

Migrations in this implementation: `0.0 → 0.1` renames `description` to
`synopsis` (`old-version/core-0.0`).

Unknown members at any open level (top level, asset, analysis, result field,
domain, warning, axis, provenance entity/activity, record payloads) survive
decode → encode at the JSON-value level: the same values, not the same
whitespace. Closed structures (`estimand`, `representation`, `underlay`,
`surface`,
`publishedDisplay` and its `threshold`/`window`, `schema` references,
provenance `edges`, warning `concerns`) reject unknown members, so a typo there
is a problem rather than a silently ignored field.

## 9. Route scheme

Browser routes (the frontend owns rendering; the server issues these in
`CommitResult`, share links, and device-login prompts):

| Route | Meaning |
| --- | --- |
| `/w/{ws}/p/{project}` | project overview: head revision, revision list, saved views |
| `/w/{ws}/p/{project}/r/{rev}` | one immutable revision (overview) |
| `/w/{ws}/p/{project}/r/{rev}/view` | explore that revision; the query string carries transient view state |
| `/w/{ws}/p/{project}/v/{view}` | a saved view (latest version) over its revision |
| `/s/{secret}` | read-only share link to one revision or one saved-view version; no login |
| `/login` | browser sign-in (`?next=` returns to the requested route) |
| `/device` | approve an `npub login` device code (`?code=` prefilled) |

Ids: `{ws}` and `{project}` are slugs chosen at creation; `{rev}` and `{view}`
are server-issued prefixed ids; `{secret}` is a random bearer secret whose hash
alone is stored.

The HTTP API lives under `/api/v1` and is defined by `modules/api-contract`:
upload sessions (`/api/v1/workspaces/{ws}/projects/{project}/upload-sessions`,
`/api/v1/upload-sessions/{session}/{objects/{digest},manifest,commit}`),
projects and revisions (`/api/v1/workspaces/{ws}/projects/{project}`,
`/api/v1/revisions/{rev}` and its `renditions/{asset}/{header,payload}`), saved
views, share links (`/api/v1/share/{secret}`), auth (`/api/v1/auth/*`), and
audit. Errors are `ApiError{code, message, head?, problems?}`.
